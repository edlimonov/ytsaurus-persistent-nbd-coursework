# КТ-1/КТ-2. Реестр нефункциональных требований

**Владелец:** Наиль Зарипов. **Версия:** 24.11.2026. **Статус:** проектные пороги на согласование. Порог — критерий будущей проверки, а не полученный результат. Перед сдачей КТ-2 каждый порог должен быть согласован с преподавателем и сверён со стендом.

| ID / категория | Требование и связь | Метрика и проектный порог | Условия и проверка | Факт |
| --- | --- | --- | --- | --- |
| NFR-001 / сохранность | Файл, записанный и синхронизированный в динамический NBD, доступен при последовательном перезапуске. BR-001, US-001/002. | 20/20 последовательных циклов «запись → `sync` → завершение → новый запуск → чтение» с точным совпадением SHA-256 файла. | Один writer на устройство, ext4, размер 1 GiB, блок 4 KiB, две тестовые ФС; стенд и SHA образа фиксируются. AT-002/005. | PLAN |
| NFR-002 / изоляция | Том не пересекает другую ФС и не монтируется вне sandbox. BR-002, US-002/003. | 100% тестовых спек с путём вне `/slot/sandbox/` и пересечением mount отклонены; 0 случаев смешивания контрольных файлов в 20 циклах. | Параметризованные тесты валидатора и два тома в джобе; AT-004/006/007. | PLAN |
| NFR-003 / безопасность доступа | Операция проверяет права пользователя на backing table и не раскрывает её данные при отказе. BR-003, US-003. | 100% сценариев «нет read», «нет write», «чужая таблица» завершаются отказом до job start; в диагностике нет токена/содержимого блоков. | Отдельные тестовые пользователи и таблицы, журнал ошибок без секретов; AT-008. | PLAN |
| NFR-004 / предсказуемый отказ | Недоступная таблица/NBD приводит к ошибке подготовки или I/O, без незаметной подмены пустым диском. BR-001/003, US-001/003. | 100% из 5 fault-прогонов имеют явный FAIL и диагностируемую причину; после восстановления прежний контрольный файл совпадает по SHA-256. | Отключение тестовой зависимости до запуска и во время I/O; таймауты фиксируются в конфиге; AT-003/012. | PLAN |
| NFR-005 / ресурсы и скорость | Подготовка и работа двух томов укладываются в согласованный бюджет стенда. BR-002, US-002. | **Кандидат:** p95 подготовки до готового mount ≤ 60 с на 20 последовательных запусках; RAM кеша ≤ `max_cached_block_count × block_size` на один том плюс накладные расходы, измеренные отдельно. | Одинаковый Linux/Porto/NBD стенд, прогретое и холодное состояние таблицы протоколируются раздельно; PERF-01. Значение 60 с требует базового замера и согласования. | PLAN |
| NFR-006 / обратная совместимость | Старые спеки без `nbd_volumes`/`nbd_mounts` продолжают запускаться. BR-004, US-004. | 100% согласованного регрессионного набора: обычная джоба, локальный `disk_request`, root data-node NBD, root dynamic-table NBD. | Запуск одинаковых спек на baseline и PR-ветке с одинаковым стендом; AT-010/011/013. | PLAN |
| NFR-007 / воспроизводимость и сопровождение | Другой разработчик может собрать и запустить тестовый путь из чистого checkout. BR-004. | Один документированный набор команд без правки исходников; CI для того же SHA проходит сборку, линтер, тесты и поиск секретов. | Изолированный runner/стенд; фиксированные версии инструментов и образов; QUAL-01. | PLAN |
| NFR-008 / наблюдаемость | Отказ можно связать с конкретной операцией/джобой/томом без раскрытия содержимого. BR-003. | Для 100% искусственных отказов в логах находятся operation/job ID, `volume_id`, стадия и причина; секретов и payload нет. | 5 fault-прогонов, анализ логов controller agent, exec node, NBD server; OBS-01. | PLAN |

**Ответственный за все NFR:** Наиль Зарипов. Преподаватель засчитывает YTsaurus и тестовый стенд как сервисную часть; до `cp2` остаётся проверить воспроизводимость на нём и согласовать NFR-005. Прочие пороги также требуют согласования. Источник метрик — будущие тестовые протоколы, не этот документ. Для stateful-части восстановление данных после сбоя хранилища будет оформлено отдельным требованием на следующем этапе после выбора модели backup/restore.

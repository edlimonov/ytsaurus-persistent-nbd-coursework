# КТ-1. User Stories и критерии приёмки

**Владелец:** Наиль Зарипов. **Версия:** 24.11.2026. **Статус:** черновик на согласование. ID `AC-xxx` уникальны внутри пакета. Все пути и данные демонстрационные.

## US-001 — сохранить файлы между последовательными запусками

**Актор:** разработчик YTsaurus-джобы. **Приоритет:** Must. **Срез USM:** MVP. **Связь:** BR-001. **Статус:** код в рабочей ветке есть, опубликованного протокола приёмки нет.

Как разработчик, я хочу подключить персистентный NBD-том по пути `/slot/sandbox/work`, чтобы повторная джоба увидела созданные ранее файлы. Триггер — необходимость перезапуска операции. Предусловия: есть смонтированная динамическая таблица корректной схемы, тестовое устройство отформатировано один раз, у пользователя есть необходимые права. Секреты не входят в спеку.

Основной путь: подготовить устройство `task/cookie/work`; задать `nbd_volumes.work` и `nbd_mounts`; запустить операцию; записать `marker.txt`; завершить; снова запустить ту же задачу с тем же cookie и томом; прочитать исходный marker и добавить новый. При ошибке подключения джоба завершается с диагностируемой ошибкой, а прежние данные не форматируются.

| ID | Given / When / Then и точный результат | Проверка |
| --- | --- | --- |
| AC-001 | Дано новое подготовленное устройство; когда стартует джоба, тогда `/slot/sandbox/work` является отдельной RW ext4, `findmnt -T` указывает на NBD, запись и чтение `marker.txt` успешны. | AT-001, интеграционный запуск |
| AC-002 | Дано завершение первой джобы после `sync`; когда запускается вторая с теми же `task`, `cookie`, `volume_id` и таблицей, тогда она читает **старое** значение `marker.txt` до новой записи. | AT-002, два последовательных запуска |
| AC-003 | Дана недоступная backing table; когда запускается операция, тогда инициализация операции или подготовка джобы сообщает ошибку и не создаёт пустую замену диска. | AT-003, fault-тест |

**Связи:** NFR-001, NFR-002, NFR-004; controller agent, exec node, NBD server, job proxy; контракт [operation-spec.md](../api/operation-spec.md); задачи T-01, T-03, T-04. **DoD:** AC-001–003 привязаны к тестам/протоколу и SHA, сборка и CI зелёные. Пока доказательство запланировано.

## US-002 — использовать два независимых каталога

**Актор:** разработчик YTsaurus-джобы. **Приоритет:** Must. **Срез:** MVP. **Связь:** BR-002. **Статус:** рабочая ветка и ручное наблюдение, повторная приёмка ожидается.

Как разработчик, я хочу в одной джобе подключить тома `notebooks` и `datasets` к разным путям, чтобы их файлы не смешивались. Предусловия аналогичны US-001; два устройства подготовлены с различными `device_id` (таблица может быть общей). После завершения первая файловая система не должна быть видна через вторую.

| ID | Given / When / Then и точный результат | Проверка |
| --- | --- | --- |
| AC-004 | Даны два разных `volume_id`; когда джоба стартует, тогда `findmnt` показывает два разных NBD-устройства на `/slot/sandbox/notebooks` и `/slot/sandbox/datasets`. | AT-004, mount inspection |
| AC-005 | Даны два каталога; когда в каждом создан файл с одинаковым именем, но разным содержимым, тогда чтение из каждого возвращает его значение; сравнение device number показывает разные ФС. | AT-004, файл и `stat` |
| AC-006 | После завершения и повторного запуска оба значения сохраняются, а файл в незамонтированном локальном каталоге sandbox отсутствует. | AT-005, два запуска |

**Связи:** NFR-001, NFR-002, NFR-005; задачи T-01, T-04. **DoD:** автоматизированный сценарий + протокол стенда с SHA. Сейчас опубликованного доказательства нет.

## US-003 — получить раннюю и понятную ошибку

**Актор:** разработчик и оператор YTsaurus. **Приоритет:** Must. **Срез:** MVP. **Связь:** BR-003.

Как автор спеки, я хочу получить ошибку до запуска джобы для небезопасного или неоднозначного mount, чтобы не потерять данные и быстро исправить конфигурацию. Триггер — отправка спеки; действие доступно только уполномоченному пользователю операции. Постусловие ошибки: джоба не стартовала и таблица не отформатирована.

| ID | Given / When / Then и точный результат | Проверка |
| --- | --- | --- |
| AC-007 | `mount_path=/tmp/work` или `.../../work`; отправка спеки → отказ с указанием пути; джоба не стартует. | AT-006, параметризованный негативный тест |
| AC-008 | Два mount с одним `volume_id` либо пересекающиеся пути; отправка спеки → отказ с указанием конфликта; джоба не стартует. | AT-007 |
| AC-009 | Указана отсутствующая/неправильной схемы таблица или нет права на чтение/запись; инициализация операции → отказ без доступа к её содержимому. | AT-008, тест прав и схемы |
| AC-010 | Для `dynamic_table` указан несовместимый `medium_name`/`account`; отправка спеки → отказ с именем поля. | AT-009 |

**Связи:** NFR-003, NFR-004; controller agent, конфиг спеки; задачи T-02, T-05. **DoD:** каждый негативный вариант имеет тест и соответствующую ошибку в контракте.

## US-004 — сохранить работу старого корневого NBD

**Актор:** текущий пользователь `disk_request.nbd_disk`. **Приоритет:** Must для совместимости, даже если публичный PR сфокусирован на томах по путям. **Срез:** совместимость MVP. **Связь:** BR-001, BR-004.

Как текущий пользователь, я хочу, чтобы прежняя спека корневого NBD продолжала работать, чтобы появление path-mounted томов не изменило существующую операцию.

| ID | Given / When / Then и точный результат | Проверка |
| --- | --- | --- |
| AC-011 | Дана прежняя спека `disk_request.nbd_disk.dynamic_table`; когда джоба стартует и пишет в корневой writable слой, тогда повторный последовательный запуск видит старый файл. | AT-010 |
| AC-012 | Дана прежняя спека датанодового root NBD без новых полей; когда она проходит валидацию, тогда предел размера и обязательные параметры сохраняют прежнюю семантику. | AT-011, регрессионный тест |

**Связи:** NFR-002, NFR-006; задачи T-06, T-07. **DoD:** два регрессионных прогона на текущем upstream baseline и ветке PR с зафиксированными результатами.

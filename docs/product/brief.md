**Владелец:** Наиль Зарипов. **Версия:** черновик 1, 24.11.2026. **Статус:** на согласование.

## Проблема и пользователь

Целевой пользователь — разработчик или команда, запускающая длительные либо повторяющиеся джобы в YTsaurus и работающая с файлами, которые должны сохраняться между перезапусками. Типовой пример — интерактивный notebook или вычислительная джоба, создающая локально видимые файлы. Операция может завершиться, но рабочие файлы нужно открыть при следующем запуске без ручного переноса из sandbox.

В текущем цикле джобы локальный sandbox и его файловая система связаны с конкретным запуском. Подготовка данных через входные артефакты и запись результата в таблицу подходит для потоковых задач, но неудобна для файловых приложений, которым нужен обычный каталог с произвольными чтениями и записями. Эта формулировка — **гипотеза о боли пользователей** до интервью и замеров; наличие технического механизма NBD само по себе её не доказывает.

Для команды эксплуатации важны управляемые точки монтирования, ограничение объёма, контроль доступа к динамической таблице, отсутствие потери данных при перезапуске и явное поведение при ошибке. Для автора YTsaurus важно сохранить совместимость старой спеки операции и старого корневого датанодового NBD.

## Предлагаемое решение и ценность

YTsaurus принимает декларацию тома в спеке операции, проверяет её, подключает NBD-устройство к динамической таблице и показывает файловую систему джобе по заданному пути внутри `/slot/sandbox/`. Стабильная пара «имя task + cookie + volume_id» адресует те же блоки при повторном запуске. Для старого корневого режима `volume_id` отсутствует. Пользователь работает с обычным файловым API; состояние находится в динамической таблице YTsaurus.

Ценность измеряется не числом новых полей в спеке, а успешным повторным доступом к файлам и уменьшением ручной подготовки/восстановления рабочей среды. Порог времени и размер экономии пока не подтверждены.

## Альтернативы

| Вариант | Сильная сторона | Ограничение для этого сценария |
| --- | --- | --- |
| Артефакты/таблицы YTsaurus | Штатный путь передачи данных | Файловому приложению нужен отдельный экспорт/импорт, нет постоянного writable каталога в одной и той же форме |
| Локальный `disk_request` | Быстрый доступ и учёт места | Данные привязаны к размещению и жизненному циклу джобы; это не гарантия сохранения между новыми операциями |
| Внешнее файловое хранилище | Готовая файловая семантика | Дополнительная зависимость, отдельные доступы и стоимость; условия сравнения нужно измерить |
| NBD на динамической таблице | Один файловый интерфейс для джобы и хранение в YTsaurus | Сложнее запуск и диагностика, требуется предварительное форматирование и защита от одновременных владельцев |

## Граница MVP

**Входит:** объявление одного и нескольких томов с `dynamic_table`; монтаж только внутри `/slot/sandbox/`; стабильная адресация при последовательных запусках; чтение ранее записанного файла; отклонение некорректных путей, пересечений и повторного использования тома в двух mount-записях; существующий корневой NBD как проверяемый сценарий совместимости; подготовка тестовой таблицы и файловой системы документированным скриптом.

**Не входит:** одновременное монтирование одной ext4 в двух независимых джобах; один том по нескольким путям; автоматическое форматирование пользовательских дисков в продуктивной операции; произвольные пути вне sandbox; дата-нодовые тома по путям; UI notebook; SLA продуктивного кластера. Дата-нодовая ветка текущего внутреннего кода будет оцениваться отдельно от публичного PR и MVP.

**Ограничения:** для интеграции нужен Linux с Porto/NBD и доступом к YTsaurus; таблица должна быть динамической, смонтированной и иметь ожидаемую схему; нужен токен/права доступа; `--yes-format` уничтожает прежнюю файловую систему выбранного устройства. В публичных материалах используются только обезличенные пути и тестовые данные.

## Источники фактов и план проверки гипотез

**Факты из кода:** в ветке `vk-25.3-nbd` есть поля `nbd_volumes`/`nbd_mounts`, валидация пути и типа backing storage, подготовка томов exec node, bind-маунты job proxy и блочное устройство динамической таблицы. Базовый SHA для этого черновика — `c983b610de7`.

**Наблюдение автора:** на внутреннем тестовом стенде два тома были видны по разным путям; после последовательного повторного запуска записанные в них строки сохранились, а локальный каталог был пустым. Это предварительное наблюдение из ручного прогона, без опубликованного протокола и без вывода о надёжности под нагрузкой.

**Гипотезы:** продукт нужен владельцам notebook и других файловых джоб; повторное восстановление workspace сейчас заметно по времени; стоимость и задержка NBD приемлемы. Проверка: 2–3 интервью либо разбор реальных сценариев с владельцами, замер времени «создать рабочее окружение заново» и повторный стендовый прогон. Интервью, цифры и согласование пока не состоялись.

| ID | Цель и заинтересованная сторона | Метрика и исходное состояние | Целевое значение / измерение |
| --- | --- | --- | --- |
| BR-001 | Пользователь повторно открывает рабочие файлы после перезапуска джобы | Доля контрольных повторных запусков, в которых контрольный файл читается без восстановления; baseline будет замерен на текущем локальном sandbox | Цель MVP: 100% из 20 последовательных тестовых повторных запусков; продуктивная цель уточняется после пилота |
| BR-002 | Пользователь разделяет рабочие файлы по независимым каталогам | Число успешно подключённых томов и отсутствие пересечения видимых файлов; baseline — один локальный sandbox | Два независимых тома в одной джобе в демонстрационном сценарии; измерение тестом и `findmnt` |
| BR-003 | Эксплуатация получает предсказуемую ошибку вместо небезопасного mount | Доля отклонённых некорректных спек до запуска джобы; baseline для новой функции отсутствует | 100% в фиксированном наборе негативных случаев из US-003; проверка автоматическим тестом |
| BR-004 | Сопровождение может принять изменение в открытый YTsaurus | Публичный PR с воспроизводимым сценарием, review и CI | PR в собственном форке и предложение в upstream; принятие PR upstream зависит от ревью и не обещается как результат курса |

## Риски

| Риск | Вероятность / влияние | Владелец | Снижение и доказательство |
| --- | --- | --- | --- |
| Один `device_id` используется двумя активными писателями ext4 | Средняя / критическое | Наиль | В MVP явное ограничение на последовательное использование; тест конфликта и проектирование механизма владения до продуктивного применения |
| Непреднамеренное повторное форматирование уничтожит данные | Средняя / критическое | Наиль | `--yes-format` только для нового устройства, документация и негативный тест повторной подготовки |
| Различие внутренней ветки и актуального upstream API усложнит PR | Высокая / среднее | Наиль | Сначала проверить актуальный upstream, согласовать контракт и сделать отдельный публичный PR с минимальным объёмом |
| Полный локальный стенд требует Porto/NBD и ресурсов | Высокая / среднее | Наиль | Отдельный доступный преподавателю тестовый стенд или согласованный симулятор; фиксировать ограничения симуляции |
| Таблица или сеть недоступна во время I/O | Средняя / высокое | Наиль | Таймауты, явная ошибка джобы, интеграционный fault-тест и инструкции восстановления |

## Согласованный формат и оставшиеся решения

По подтверждению автора, преподаватель разрешил использовать рабочий проект и засчитывает существующий YTsaurus с тестовым стендом как **сервисную** часть курсовой. Учебный пакет размещается в отдельной папке рядом с YTsaurus; публичный PR автор подготовит в своём форке. Перед `cp1` остаётся утвердить продуктовые гипотезы и пороги НФТ; перед `cp2` — предъявить доступный проверяющему прогон, CI и SHA. В учебных доказательствах не должно быть внутренних адресов и недоступных проверяющему ссылок.
